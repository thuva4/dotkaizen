# Local versions and coordinated writes

This protocol applies to every mutation under `~/.domains/`, including the global catalogue, learning records, pending entries, and recovery. It coordinates cooperating agents on one local filesystem. Before discovery or reading, follow [read memory](read-memory.md) for consistent snapshots. Manual editors and tools that ignore the protocol can still interfere.

## Acquire a short global lock

1. Expand the home path. Create the root directory if needed. Acquire exclusion with one ordinary `mkdir ~/.domains/.write-lock` command. Do not use `mkdir -p` for the lock. Directory creation is atomic on the local filesystem. A failed acquisition means no shared writes, including Git initialization or lock metadata edits.
2. After acquisition, create `.write-lock/owner.md` with a unique task token, task description, host, and start time. Record the token in session context. Keep this directory across tool calls; a shell-exit trap must not release it while later tools are still editing.
3. A held lock permits read-only source investigation elsewhere. Defer memory edits or retry once at the next reconciliation point. Do not repeatedly poll, steal a lock because it is old, or assume a missing owner file means it is free. A crash can occur between acquisition and metadata creation.
4. The owning session releases only its own lock, after checking the token. Remove its owner file, then use `rmdir` on the lock directory. Never recursively delete it. Acquire once for the full multi-page update, then release promptly. Do not hold it while waiting for human answers.

Stale-lock recovery requires explicit user recovery direction or confirmation from the actual owning session that it finished. Inspect unfinished diffs first. A dead PID or old timestamp alone is insufficient proof of ownership or safe recovery. Do not erase pending work while clearing a lock.

## Save local history

While holding the lock, ensure the root has its own Git repository. Check its actual top-level path. If no root-local `.git` exists, use `git init <expanded-root>`; a parent project's repository is not sufficient. Never change global Git identity or configure a remote. Ignore `.write-lock/` and `.recovery/` in the root's `.gitignore` before staging.

Inspect `git status`, staged changes, and affected diffs. If unrelated staged changes exist, defer the Git write and return a handoff; do not unstage or commit them. Preserve unrelated unstaged files. Before modifying canonical files, copy their exact current contents to a unique `.recovery/<task-token>/` directory, preserving relative paths and recording which files were absent. Write a short manifest of affected paths, the pre-edit HEAD if present, and interruption status. Do not overwrite an earlier recovery directory. This raw recovery checkpoint is ignored by Git and excluded from discovery and factual reads. It preserves incomplete or manual edits without publishing them as reader HEAD. Report the checkpoint path. Existing coherent commits remain the published baseline.

For the initial published snapshot, include only actual knowledge Markdown files and the knowledge-root `.gitignore`; review the file list and validate citation and page consistency before committing. If an existing collection is too large or incoherent to validate within the pass, defer initialization and return a scoped proposal rather than publishing an unchecked baseline. For routine updates, stage only the exact affected paths. Do not use `git add .`, `git add -A`, or commit unrelated content. Re-read and reconcile immediately before mutation. Allocate IDs from the latest register. Check the staged diff, citations, links, scope, and consistency against the staged tree that will become the published snapshot, using staged files such as `git show :<path>`. Unstaged or untracked sources cannot satisfy an internal citation in that tree. External source locators remain evidence references, not internal pages. Commit the coherent change locally. Record the commit ID in the task report. Empty updates need no commit.

If Git is absent or identity is not configured, continue the project investigation and return a proposed memory update. Do not mutate canonical notes without a raw recovery checkpoint for existing content and a usable local Git repository. If a commit fails after edits, report uncommitted paths and leave the lock with an interruption note for explicit recovery. Do not describe that state as reconciled or let another writer commit it unknowingly.

## Recover without losing newer work

For a normal version restore, inspect history with `git log -- <path>` and preview with `git show <commit>:<path>`. Explain which facts and dates would return. Acquire the lock and preserve current affected files in a new raw checkpoint. Restore only the requested files or sections, reconcile linked explanations, and commit the recovery as a new change. Never reset the whole repository or overwrite unrelated files.

For an interrupted update, inspect the existing lock owner, raw manifest, unfinished diffs, and published HEAD if one exists. With explicit recovery direction, first preserve the interrupted files in a separate raw checkpoint, then clear the stale lock as authorized and acquire a new owned lock. If the session still owns the lock, retain that ownership throughout recovery. Choose the requested outcome: complete and validate the pending update, or restore the pre-edit files from the earlier raw copies. Restore only affected staged paths to their pre-edit state, preserving unrelated staging. For paths marked absent in the earlier manifest, remove only the task-created files after preserving their interrupted contents. Missing copies or ambiguous later edits require a focused question before dependent restoration.

This raw-copy route works even when the first commit failed and no HEAD exists. A restored empty initial state needs no fabricated commit; report that no published snapshot exists. A recovered coherent collection can receive its first commit after validation. Do not disable hooks, signing, or identity settings to force a commit. If the original commit failure remains, keep the interruption explicit and defer publication. Release only the owned lock when recovery leaves a safe, understood state.

Local Git supplies history, not an external backup. Disk loss still requires an independently chosen backup. Multi-file writes are not crash-atomic; the lock plus committed-reader protocol exposes only coherent committed snapshots to cooperating readers. A leftover lock or failed commit requires recovery before further canonical writes.
